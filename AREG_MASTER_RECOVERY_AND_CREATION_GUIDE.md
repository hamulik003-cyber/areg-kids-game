# 1. Planet / 360° UV creation pipeline

This is the canonical method that produced the successful planet maps.

## A. Reference first
1. Start from the approved visual in the **Մոլորակներ** gallery.
2. Match the reference's color palette, tonal balance, major markings and overall texture identity.
3. For Saturn/Uranus or any ringed body, the generated UV must contain **the body only**. Rings stay separate 3D geometry.

## B. Generate the map
1. Create a **true 360° equirectangular 2:1 UV map**.
2. No collage, no perspective planet render, no background, no ring, no decorative border.
3. Preserve the approved reference colors as closely as possible. Do not apply extra grading.
4. One object per image.
5. The texture must tile correctly around a sphere.

## C. Validate before integrating
1. Verify exact 2:1 aspect ratio.
2. Preserve the original uploaded/generated bytes whenever possible. Do not recompress casually.
3. Compare the texture on a rotating 3D sphere against the original approved reference.
4. Confirm seam/front alignment before finalizing.

## D. Repository placement
Canonical final planet maps live under:

`assets/space3d/user-final/`

Examples:
- `01-sun.png`
- `02-mercury-v2.jpg`
- `05-moon-v2.jpg`
- `08-saturn.png`
- `09-uranus.png`

The exact planet-to-file mapping is stored in `FINAL_UV_PATHS` inside `space-3d-games.js`.

## E. Three.js exact UV pipeline
The successful path is:

1. `prepareUserUvTexture(item)`
2. repo-first lookup via `prepareRepoUvTexture(item)`
3. image load via `loadTrue360Image(...)`
4. create texture with `exactUvTextureFromImage(img)`

Important texture settings:
- `THREE.SRGBColorSpace`
- `wrapS = THREE.RepeatWrapping`
- `wrapT = THREE.ClampToEdgeWrapping`
- `minFilter = THREE.LinearMipmapLinearFilter`
- `magFilter = THREE.LinearFilter`
- anisotropy = 16

For approved user UVs, `spherePlanet()` uses:
- `THREE.MeshBasicMaterial`
- `color: 0xffffff`
- `toneMapped: false`

Front alignment:
- `mesh.rotation.y = -Math.PI/2`

This is deliberate: it keeps the generated map's color/appearance from being altered by scene lighting or tone mapping.

## F. Fallback
IndexedDB remains only as a fallback:
- DB: `areg-space-user-uv-v1`
- store: `textures`

Permanent approved maps should always be committed to GitHub so they survive browser/cache/data loss and work on every device.

# 2. Special geometry rules — do not break

## Saturn and Uranus
- Body UV and ring are separate.
- Never bake rings into the 2:1 body texture.
- Current approved v205 ring architecture is split into:
  - back half
  - planet
  - front half
- This creates the correct physical impression that the planet sits inside the ring.
- Both use a shared tilted `axisPivot`.
- Uranus keeps retrograde body spin.
- Uranus icy debris is split front/back so particles do not visually orbit through the wrong side.

## Phobos / Deimos
Do not replace the approved irregular geometry with a perfect sphere.
Their geometry uses procedural vertex perturbation and approved non-uniform scale.
Texture changes only unless explicitly requested.

## Haumea
Do not change the approved oval geometry:
- sphere scale approximately `(1.28, .78, .88)`
- display roll approximately -31°
Its ring remains a separate 3D object attached to the body's surface/axis behavior.

## Solar System / Milky Way / Black Hole
These are special bespoke 3D objects, not normal 2:1 UV spheres.

# 3. Safe integration sequence for every new planet-map change

1. Inspect current `main`.
2. Create a recovery branch before risky visual/geometry changes.
3. Add/replace only the requested asset.
4. Update `FINAL_UV_PATHS` only if the canonical filename changes.
5. Keep repo-first texture loading.
6. Do not alter unrelated planet geometry.
7. Bump app/build version.
8. Bump DotKiosk launcher version.
9. Bump service-worker cache version.
10. Update comparison page loader if needed.
11. Push to `main`.
12. Wait for GitHub Pages deployment to report **success**.
13. Test in browser and DotKiosk.
14. Compare visually against the approved reference.
15. Only after user approval, create a new safe snapshot/recovery ref.

# 7. Phone safety / persistence

The phone/DotKiosk copy is **not** the source of truth.

The durable source of truth is GitHub:
- source code
- permanent images/audio/assets
- commit history
- recovery branches
- GitHub Pages deployment

If DotKiosk is removed, iOS clears website data, Safari cache is erased, or the phone is replaced, the game can be reopened/reinstalled from the GitHub Pages URL as long as the repository remains intact.

Therefore:
- permanent content must live in GitHub, not only IndexedDB/localStorage
- localStorage should be used only for user progress/settings
- approved generated assets must be committed to the repository
